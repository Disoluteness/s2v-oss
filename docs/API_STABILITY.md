# API 稳定性与弃用政策

状态：自 **1.0.0** 起生效（ADR-006）；当前版本 **1.1.0**

这份文件回答一个只有一句话的问题：**哪些东西我可以依赖，哪些东西明天可能变。**

它不是「我们承诺永远不改」——那种承诺会在第一次必须改的时候被撕掉。它是一份**分类表**：
把接口分成三档，每档写清改动代价。集成方只需要知道自己在哪一档上。

## 1. 三个面

| 面 | 包含什么 | 改动规则 |
|---|---|---|
| **稳定面** | `/api` 下除实验面之外的全部端点；请求/响应 schema（OpenAPI 文档里的）；HTTP 状态码与错误信封；错误码字符串与 `category` / `retryable`；权限键；webhook 事件名与事件载荷结构；`X-S2V-Signature` 签名格式；幂等键语义；分页约定 | 见 §2 的分类表。**只增不改**是默认 |
| **实验面** | `GET /metrics`；HTML 页面（`/workspace` 等 7 条，`include_in_schema=False`）；`X-Embed-Token` 令牌的**内部载荷**；上游供应商回调 `/api/provider-callbacks*` 的形状；`GET /api/deployment` 的**字段集合**（字段含义稳定，可能**新增**字段） | 无公告即可变更，但**移除**既有字段仍会记一条 CHANGELOG |
| **不承诺面** | 内部实现：数据库表名与列、审计 payload 的具体键、日志行格式、缓存键、`X-Request-Id` 的取值格式、进程内指标 | 随时可变，不需要理由 |

把它显式写出来是有代价的：一旦某个东西进了稳定面，改它就要走流程。所以判断「进哪一面」的
标准是**调用方会不会因为这次改动而静默出错**——不是「它看起来重不重要」。`/metrics` 看起来
重要，但它的标签集服务于本平台的观测需要，把标签集钉死等于把运维便利变成对外负债，所以它是
实验面。错误码字符串看起来只是一个字符串，但调用方拿它写 `if code == "team_quota_exceeded"`，
所以它是稳定面。

## 2. 稳定面的兼容规则

判据始终是同一句：**改动之后，一个按旧文档写的客户端会不会因此出错。**

| 改动 | 允许？ | 理由 |
|---|---|---|
| 新增端点 | ✅ 随时 | 旧客户端不调用它 |
| 新增**可选**请求字段 | ✅ 随时 | 不传就是旧行为 |
| 新增响应字段 | ✅ 随时 | 旧客户端忽略不认识的键（见 §4 的宽容要求） |
| 新增错误码 | ✅ 随时 | 旧客户端只会走到 `else` 分支；**新码必须同时在 `GET /api/error-codes` 出现** |
| 新增 webhook 事件类型 | ✅ 随时 | 订阅方按事件名分发；未订阅的类型不会推给它 |
| 新增权限键 | ✅ 随时 | 老身份不会被**新**键收窄 |
| 新增**必填**请求字段 | ❌ 须弃用流程 | 旧客户端不传 → 422，静默失效 |
| 删除响应字段 / 改字段类型或语义 | ❌ 须弃用流程 | 客户端读到 `None` 或错的类型，往往不报错 |
| 收紧既有校验（更严的正则、更小的上限） | ❌ 须弃用流程 | 曾通过的输入开始被拒 |
| 改路由路径 / 改 HTTP 方法 | ❌ 须弃用流程 | 404/405 |
| 改错误码字符串或给它换 `category` / `retryable` | ❌ 须弃用流程 | 会把调用方的重试逻辑带错方向 |
| 拓宽既有权限键的持有者 | ⚠️ 记 CHANGELOG | 不会让任何调用方失败，但会改变「谁能看到什么」，需要让人知道 |
| **收窄**权限键的持有者 | ❌ 须弃用流程 | 开始 403 |

最后两条是同一件事的两面，分开写是因为它们的代价不对称：拓宽是别人多看见一点，
收窄是别人突然做不了他昨天在做的事。**收窄按破坏性变更处理**——V8.4 把 5 条
`provider-credentials*` 端点从免鉴权改为需要 `provider:manage` 就是一次这样的变更，
它被记进了 `CHANGELOG.md` 而非默默发布。

## 3. 弃用流程

最短路径，四个步骤，刻意保持可执行：

1. **双跑**：新形状上线，旧形状**同时**继续工作。响应里带上弃用标记
   （HTTP `Deprecation` 响应头 + `Sunset` 日期），`GET /api/error-codes` 或端点文档里写明替代方案。
2. **记一条**：`CHANGELOG.md` 的 `Deprecated` 段落下记录，注明替代写法与计划移除的版本。
3. **跨一个次版本**：移除最早发生在下一个 `1.x` 里程碑。此处「版本」指本项目的里程碑版本
   （路线图里的一项），不是两周一次的迭代。
4. **移除**：进 `Removed` 段，同时删除弃用标记。

这条流程没有第 3 步之外的时间下限，也没有「必须保留 N 个月」的字面量——它的目的是**给一次
升级窗口**，而不是制造一个没人执行的日历。任何一次移除都必须在 CHANGELOG 里能被找到。

## 4. 对客户端的两个要求（换取稳定面承诺）

稳定性是双向的。为了让我们能「随时新增响应字段」，客户端必须：

1. **忽略不认识的键**，不要对未知字段报错，也不要依赖字段顺序或「恰好这么多字段」。
2. **按 `code` 而不是按 `message` 分支**。`message` 是给人看的，措辞随时可能更通顺；
   `code` 才是契约，它来自 `GET /api/error-codes` 的目录。
   `category`（用于粗粒度分类）与 `retryable`（用于决定要不要重试）同样是契约的一部分。

两个官方 SDK 已经遵守这两条；如果你自己写客户端，这是升级不会坏掉的前提。

## 5. 版本号的含义

`info.version` / `app_version` 是**同一个常量**（`apps/api/app/version.py`），也是本文件生效的版本。

- **主版本**只在「稳定面的兼容规则发生变化」时抬——1.0.0 的含义是**这份政策开始生效**，
  而不是接口形状发生了变更（它没有）。
- **次版本**对应路线图里的一项里程碑（V8.x 的每一项）。**1.1.0**（V1.1 能力补齐）是政策生效后的
  第一次兑现：全部为**增量**变更（新端点 / 新可选字段 / 新错误码 / 目录扩充），稳定面形状一字未动，
  按 `1.0.0` 写的客户端无需改动。
- 修复类改动不与里程碑绑定，直接进最新版本。

SDK 的版本与服务端**解耦**：`s2v` 与 `s2v-client` 各自独立发布，客户端版本不是关于服务端的陈述。

## 6. 这份政策怎么被验证

文档承诺如果没人检查，等于没有承诺。两层断言：

- `tests/test_release.py`——版本三处一致、错误码 / webhook 事件 / pipeline 目录 / 权限键的
  计数与字段被钉住；改动它们会让测试失败，逼迫改动者回来读这份文件。
- 部署门禁第 25 节 `verify_release`——从**运行中的实例**（只走 HTTP）重复同一批断言。
  测试钉住仓库里的代码，门禁钉住部署机上的那个镜像。

此外 `tests/test_openapi_contract.py` 钉住一条更强的不变式：
`POLICY` ∪ `OPEN_ENDPOINTS` 与 OpenAPI 文档里的端点**精确相等**——
没有任何端点能绕过权限表静默出现在 spec 里，反之亦然。

## 7. 明确不做

- **不做多版本并行（`/api/v1` 与 `/api/v2` 同时在线）**。当前只有一种部署形态、一类集成方，
  版本并行的运维成本（两份文档、两条回归路径、双份门禁）远大于收益。路径前缀保持 `/api`，
  版本由 `info.version` 表达。真需要 breaking change 时，先改的是这份判断。
- **不做 SLA 与弃用时间表公示**。本政策是**兼容性**承诺，不是**可用性**承诺；
  可用性归部署方（见 `docs/DEPLOYMENT.md` 第 12 节的明确不覆盖清单）。
- **不把实验面当二等公民**。实验面同样有测试与门禁覆盖，只是**不承诺形状**——
  `/metrics` 的标签集可以变，不会变的是它一直可用且不泄漏租户数据。

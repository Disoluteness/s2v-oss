# V6.5 Team / Permission 实施计划

- 文档版本：v1.1
- 编写日期：2026-10-09
- 归属版本：V6 Web Studio 与团队协作版（路线图第 5 项，V6 收尾）
- 状态：**已完成**（落地清单与验证见 §7）

## 1. 目标

让平台从「单机单页工作台」变成「一个团队可同时管理多个项目与多个 run」的内部 Studio，
并让权限与关键操作审计可被查询。承接路线图 V6 的两条验收标准：

- 一个团队可同时管理多个项目和多个 run。
- 所有关键操作有审计记录。

V6.5 同时是 V8.3（team quota / 计费归因）的前置：没有团队与成员概念，团队级配额无处挂载。

## 2. 现状与缺口

| 对象 | 现状 |
|---|---|
| `tenants` | 已存在，全系统默认 `DEFAULT_TENANT_ID` |
| `users` | 已存在（T77 起由 `UserRepository.ensure_user` 按需登记外部审核人） |
| `projects` | 已存在，带 `tenant_id` / `created_by` |
| 身份识别 | **完全没有**。API 无鉴权、无中间件、无 request 级 actor |
| 权限 | 无 `teams` / `memberships` / `permissions` 表 |
| 审计 | 只有 run 级 `event_logs`（`run_id` 非空），跨实体操作（建项目、加成员）无处记录 |

关键约束：**既有调用方（含部署门禁脚本、MVP 样片链路、全部单测）不带任何身份信息**，
因此权限方案必须向后兼容——默认身份必须是一个拥有全部权限的内部管理员。

## 3. 概念模型

```
tenant（已有）
  └── team（新增）           团队：租户内的协作单元，默认一个 DEFAULT_TEAM
        └── team_membership（新增）   用户 ↔ 团队 + 角色
  └── project（已有）
        └── project_membership（新增）用户 ↔ 项目 + 角色（在团队基线之上提权/降权）
  └── audit_log（新增）      跨实体审计流水，带 actor
```

- **team 角色**：`owner` / `admin` / `member` / `viewer`。
- **project 角色**：`owner` / `editor` / `reviewer` / `viewer`。
- **生效权限 = 团队角色权限 ∪ 项目成员权限**（并集，取宽）。项目角色用于在团队基线上做加减。

### 3.1 权限键

| 权限 | 含义 |
|---|---|
| `project:read` | 查看项目、仪表盘、run 列表 |
| `project:write` | 新建/修改项目 |
| `project:delete` | 归档/删除项目 |
| `run:read` | 查看 run、产物、job、事件 |
| `run:create` | 新建 run |
| `run:start` | 启动 run（含接受意图降级、付费确认） |
| `run:write` | run 状态动作、重跑、派发、修复输入 |
| `run:review` | 审核决策、评论、指派（门禁动作） |
| `asset:read` | 查看资产 |
| `asset:write` | 上传/生成资产 |
| `library:read` | 查看资产库 |
| `library:write` | 资产库集合与条目写入、沉淀、复用 |
| `member:read` | 查看成员与权限矩阵 |
| `member:manage` | 增删改团队成员与项目成员 |
| `team:manage` | 团队本身的建改删 |

### 3.2 角色 → 权限矩阵

团队角色：

| 角色 | 权限 |
|---|---|
| `owner` | 全部（含 `team:manage`、`project:delete`、`member:manage`） |
| `admin` | 除 `team:manage` 外全部 |
| `member` | `project:read` / `project:write` / `run:*`（除无） / `asset:*` / `library:*` / `member:read`，不含 `project:delete` / `member:manage` / `team:manage` |
| `viewer` | 所有 `*:read` |

项目角色：

| 角色 | 权限 |
|---|---|
| `owner` | 项目范围内全部（含 `project:delete`、`member:manage`） |
| `editor` | 项目范围内除 `project:delete` / `member:manage` 外全部 |
| `reviewer` | `project:read` / `run:read` / `run:review` / `asset:read` / `library:read` |
| `viewer` | 项目范围内所有 `*:read` |

## 4. Actor 解析

`resolve_actor(request)` 按顺序解析：

1. **受信头**：`X-Actor-Id`（可选 `X-Actor-Name`）。
   - `ACTOR_TRUST_MODE=open`（默认）：直接信任，用于内部网关/单租户部署。
   - `ACTOR_TRUST_MODE=secret`：必须带 `X-Actor-Secret` 且等于 `ACTOR_HEADER_SECRET`，否则回退默认身份。
2. **回退默认身份**：`DEFAULT_ACTOR_ID`（默认 `system`），保证既有调用方不被破坏；
   该身份在初次使用时按 `owner` 登记到默认团队。

`ActorContext` 字段：`actor_id` / `display_name` / `tenant_id` / `source`（`header` | `default`）。

### 5.2.1 显式开放清单（`OPEN_ENDPOINTS`，18 条）

「不铺」不等于「忘了铺」。未纳入 `POLICY` 的端点必须逐条登记进同文件的 `OPEN_ENDPOINTS`，
并写明理由；测试断言 `POLICY` ∪ `OPEN_ENDPOINTS` **精确等于**全部注册路由（且两者不相交），
因此新增端点无法在无人决策的情况下悄悄逃逸。

| 端点 | 开放理由 |
|---|---|
| `GET /api/health` | 存活探针 |
| `GET /api/error-taxonomy` | 静态错误分类字典 |
| `GET /api/permissions` | 静态权限矩阵，供页面渲染，不含租户数据 |
| `GET /api/pipelines` | 流水线定义 |
| `GET /api/render-profiles`、`/{profile_key}` | 渲染档位定义 |
| `GET /api/run-state-transitions` | 状态机元数据 |
| `GET /api/tools`、`/capabilities`、`/providers`、`/{tool_key}` | 工具目录 |
| `GET /api/me` | 身份自举：判断权限之前必须先能回答「我是谁」 |
| `GET/POST/PATCH /api/provider-credentials*`、`POST /{id}/check` | provider 密钥安全归 V8.4；V6.5 不引入 provider 级权限键（见 §6） |
| `POST /api/provider-callbacks/{provider}` | 调用方是上游供应商而非平台身份，无可解析的 actor；真实性属签名校验（V8.4） |

### 5.3 审计

`audit_logs` 记录：`actor_id`、`action`（如 `team.created` / `team.member_added` /
`project.member_role_changed` / `project.member_removed` / `permission.denied`）、`entity_type`、
`entity_id`、`project_id`（可空）、`summary`、`payload`、时间。

权限拒绝本身也是一次可审计事件：`require_permission` 先写入 `permission.denied` 并提交，
再抛 `PermissionDenied`，因此拒绝记录不会随请求中止而回滚。

说明：路线图把 `audit_logs` 列在 V8 的 migration 清单里。V6.5 提前引入，原因是 V6 的验收标准
（"所有关键操作有审计记录"）需要它，而 `event_logs.run_id` 非空、无法承载跨实体操作。
这是一次**有意的偏差**，V8 到时只需在此表上扩展（保留字段、保留查询接口），不重复建表。

## 6. 明确不做的事

- 不做真实登录（密码 / 会话 cookie）与外部 IdP（OIDC / SAML）对接。身份由内部平台网关注入。
- 不做 V7 的 `api_keys` / scopes / 幂等键（那是面向 SDK 的编程访问，与 V6.5 的「请求身份」不同）。
- 不做配额与计费归因（V8.3）。
- 不做 provider key 加密、签名 URL、上传扫描（V8.4）。**连带地，本版不给 provider 密钥端点加权限**：
  引入 provider 级权限键会把「谁能配置付费 provider」这一 V8.4 的题提前拍定。这 6 条端点因此被
  显式登记在 `OPEN_ENDPOINTS` 里（§5.2.1），是**有记录的取舍**而不是遗漏；V8.4 落地时应把它们
  从 `OPEN_ENDPOINTS` 移入 `POLICY`。
- 不给所有端点铺权限依赖：除 §5.2 表格列出的高价值变更端点外，其余一律进 `OPEN_ENDPOINTS` 并写明理由。
- 不改变 `DEFAULT_TENANT_ID` 单租户假设；多租户路由（子域名 / 路径前缀）留待后续。

   用未登记身份逐个打真实请求，断言一律 403。它同时证明「策略可达」与「未入座即无权限」，
   任何查表漏配都会立刻变成非 403。

## 8. 已知边界与后续

- `X-Actor-Id` 只是**受信头**：默认 `ACTOR_TRUST_MODE=open`，任何能直连 API 的客户端都能自称
  任意身份。对公网暴露前必须切到 `secret` 模式并配置 `ACTOR_HEADER_SECRET`（该模式下未配置密钥
  时不信任任何头，一律回退默认身份）。真正的身份体系仍在网关 / IdP。
- provider 密钥类端点按 §6 保持开放，待 V8.4 接管。
- 团队级配额与计费归因（V8.3）已具备前置表结构，但本版不实现。
- `project_memberships` 目前不参与「谁能看到哪些项目」的列表过滤：`GET /api/projects` 返回租户内
  全部项目（受 `project:read` 约束）。项目级可见性收敛留待 V8.3 一并设计。

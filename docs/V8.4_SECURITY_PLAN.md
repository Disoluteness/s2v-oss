## 1. 目标与范围

V6.5 在 `permission_policy.py` 里显式登记了 6 条「暂不设权限」的 provider 端点，理由写着
「provider 密钥安全归 V8.4」——本项就是来收这个口的。四件事：

1. **provider 密钥落盘加密**——新增 `encrypted_secrets` 表，provider 凭证的密钥材料
   以 AES-256-GCM 密文存放，`provider_credentials.secret_values` 只留**不透明引用**；
2. **provider 密钥端点接管**——把 5 条 `provider-credentials*` 端点从 `OPEN_ENDPOINTS`
   移入 `POLICY`，由新权限键 `provider:manage`（租户级）把关；第 6 条（供应商回调）
   无平台身份、**不能**进 `POLICY`，改为**签名校验**；
3. **上传与资产链接的入口加固**——上传加编码长度/解码大小上限与 MIME 白/黑名单 +
   魔数嗅探；资产签名链接加 TTL 上限与「生产环境仍用默认密钥则拒绝签发」的守卫；
4. **敏感操作审计**——密钥写入/轮换/迁移、凭证变更与健康检查逐条落 `audit_logs`。

**明确不做（记录取舍）**：

- **不做真实杀毒 / AV 引擎**。「文件类型扫描」在这里的可行含义是**魔数嗅探 + 类型
  白名单**（拒绝「声明是 mp4、开头是 ELF/MZ/脚本 shebang」这类伪装），不是 ClamAV
  集成——那是一个独立进程、独立特征库更新通道与独立运维面，收益不抵一个内部 Studio
  的风险模型。
- **不做 KMS / 云 HSM 集成**。主密钥来自环境变量，与 `api_key_pepper` /
  `embed_token_secret` 同一档：**持有环境变量的人即持有密文**。这也是为什么加密默认
  关闭（见 §2.1）——不假装单靠一张表就能防住已经拿到数据库的人。
- **不做密钥版本表 / 自动再加密**。`encrypted_secrets.key_version` 只做标注；
  轮换 = 换 `SECRET_ENCRYPTION_KEY` + 调 `POST .../rotate` 重加密（runbook 见 §2.1）。
  建一张版本表需要一套「哪个版本解密、什么时候重加密」的调度，本项不做调度。
- **不做新页面**（与 V8.1 / V8.2 / V8.3 同口径）。
- **不引入新权限的读键**。见 §2.2：provider 凭证的读接口带**部分密文**（`secret_preview`
  是 `前 3 字符 + 后 4 字符`），「谁能看」与「谁能改」在这里是同一件事，因此只有
  `provider:manage` 一个键，不设 `provider:read`。
- **不动 API key / webhook secret 的存储形态**。API key 存哈希（不可逆，已经是对的）；
  webhook secret 明文回显是 V7.3 的**有意设计**（订阅者要用它验签）。`encrypted_secrets`
  服务的是「平台需要还原出明文去用」的密钥，即 provider 凭证与未来的同类材料。

## 2. 设计决策

### 2.1 provider 密钥落盘加密：默认关闭的 opt-in

**核心判断：加密是 opt-in，`SECRET_ENCRYPTION_KEY` 未配置时行为与 V8.3 完全一致。**
理由与 V8.2 的 `LOG_FORMAT=json` 相同——加密打开的瞬间，「谁能还原明文」从一个
进程内的问题变成一个**运维**问题（环境变量会不会随备份一起丢、随镜像一起进仓库）。
把它设成默认开启，等于让每个现有部署在不知情的情况下多了一个「丢了就没法调用 provider」
的单点；设成显式 opt-in，则打开它的团队一定知道自己在承诺什么。

加密开启后的数据流：

```
写：DTO secret_values={"DASHSCOPE_API_KEY": "<明文>"}
      -> SecretBox.encrypt(tenant_id, name, 明文) -> 密文
      -> INSERT encrypted_secrets(id=sec_xxx, name, ciphertext, key_version)
      -> UPDATE provider_credentials.secret_values={"DASHSCOPE_API_KEY": "sec_xxx"}
读：secret_values["DASHSCOPE_API_KEY"] == "sec_xxx"
      -> SELECT encrypted_secrets WHERE id='sec_xxx'
      -> SecretBox.decrypt(...) -> 明文（用于 preview 与 environment_overrides）
```

- **`secret_values` 的语义**：从「名字 → 明文」变成「名字 → **定位符**」。托管的定位符是
  `sec_<hex>`（不透明、不含秘密内容）。**未加密时**写入的仍是明文（兼容路径）。
  **加密开启后遇到一个非托管定位符的值**，视为 **V8.4 之前的遗留内联密钥**：
  仍然可读可用（不会静默失效），但凭证视图会把它标为 `encrypted=false`，
  并可由 `POST /api/provider-credentials/{id}/rotate` 一次性迁入密文表。
  这个「一个字段两种形态」的窗口是**有界的**：团队调一次 rotate 即彻底退出。
  取舍的理由——迁移时无法保证密钥已配置（migration 不该依赖运行时秘密），
  而 GET 路径写库（惰性迁移）会在只读接口上制造副作用，两者都比一个显式
  `rotate` 端点差。
- **算法**：AES-256-GCM（`cryptography` 库），12 字节随机 nonce，与密文一起 base64。
  **AAD 绑定 `tenant_id` + `name` + `key_version`**——这样一行的密文被挪到别的租户、
  别的密钥名下都会解密失败，而不是「解出来了但张冠李戴」。
- **主密钥派生**：`sha256(SECRET_ENCRYPTION_KEY.encode())` 得到 256 位。
  接受任意高熵字符串（推荐 `openssl rand -base64 32`），不做 base64 长度校验——
  校验只会制造一种「配了但因为格式不对而静默退化成明文」的失败模式，
  而哈希化让任何输入都稳定映射到一把 32 字节密钥。
- **轮换 runbook**：换 `SECRET_ENCRYPTION_KEY` → 对每个凭证调一次 `rotate`。
  在 rotate 完成前，旧密钥的密文解不开，凭证会报 `encrypted=false` 且
  `environment_overrides` 拿不到值（provider 调用失败，**不会**拿错误密钥静默降级）。

### 2.2 provider 密钥端点接管：5 条进 POLICY，回调靠签名

- **5 条进 `POLICY`**，权限键 `provider:manage`，作用域 `SCOPE_TENANT`：
  `GET /api/provider-credentials`、`GET /api/provider-credentials/{id}`、
  `POST /api/provider-credentials`、`PATCH /api/provider-credentials/{id}`、
  `POST /api/provider-credentials/{id}/check`。
  - 放在 `SCOPE_TENANT` 而非 credential 作用域：凭证本身可以挂在某个 `project_id`
    上，但**密钥的可见性是租户级的**——一个项目成员能读到「本租户配了哪些 provider
    密钥、里面某个的前 3 后 4 位」是越权的。
  - `provider:manage` 进 `TENANT_ONLY_PERMISSIONS`（第 6 个）。理由与
    `api_key:manage` 同构：能写 provider 密钥的人，等于**能控制整个租户的付费调用
    走哪个账号**；把它交给项目角色，就是允许一个项目的成员替整个租户刷 provider 账单。
  - **check 端点也用 `provider:manage`**：它会写 `last_check_*`（一次变更）并且会
    实际触碰凭证，不是读。
- **第 6 条 `POST /api/provider-callbacks/{provider}` 留在 `OPEN_ENDPOINTS`，但加签名校验。**
  它进不了 `POLICY` 的原因很直白：`POLICY` 的每一项是「(方法, 路径) → (权限, 作用域)」，
  而回调的调用方是**上游供应商**，不是平台身份，没有任何 actor 可以判定权限——
  硬塞进去就等于发明一个「谁也拿不到」的权限。所以它保持开放，但把 V6.5 那条
  「真实性属签名校验（V8.4）」的理由升级成**已实施**：
  - 配置了 `PROVIDER_CALLBACK_SECRET` 时，要求 `X-S2V-Signature: t=<unix>,v1=<hex>`
    （HMAC-SHA256 over `"{t}.{body}"`，**与 V7.3 webhook 完全同构**，只是密钥来自配置
    而非订阅行），时间戳在签名串里 → 同时拿到防篡改与防重放；
    缺失/不匹配/超容差一律 401 `provider_callback_invalid`（**不区分原因**，同
    `api_key_invalid` / `embed_session_invalid` 的「不做 oracle」立场）。
  - 未配置时维持现状（接受，因为本地与门禁都要能跑）——这是 opt-in 的又一处体现，
    但理由与 §2.1 不同：回调的真实性来自**上游怎么配**，平台无法替它做主。
- **新增 `POST /api/provider-credentials/{id}/rotate`**（`provider:manage` / tenant）：
  把该凭证的**内联遗留密钥迁入密文表**，并**用当前密钥版本重加密已有引用**——
  一个端点同时覆盖「升级迁移」与「主密钥轮换」两条 runbook。幂等。
- **审计**：凭证创建 / 更新 / 检查 / 轮换逐条落 `audit_logs`，`payload` 只记
  **字段名与数量**（`secret_names`），**绝不记值**。

### 2.3 上传加固：编码长度、解码大小、类型与魔数

现状：`upload_asset` 对 `content_base64` 无任何上限，也不看类型——一个 2 GB 的字符串
会先进内存再解码，且「声明 mp4 实为可执行文件」会原样落到对象存储、随后被
`/assets/{id}/content` 以 `mime_type` 回吐。V8.4 在**解码之前**设三道关卡：

1. **编码长度闸**：`len(content_base64)` 超 `ASSET_UPLOAD_MAX_BYTES * 4/3 + 余量` 直接
   413。先于 `b64decode`，避免「先吃下整个字符串再发现超限」。
2. **解码大小闸**：解码后 `len(content) > ASSET_UPLOAD_MAX_BYTES` → 413
   `payload_too_large`（默认 256 MiB）。
3. **类型闸**：`ASSET_CONTENT_TYPE_DENYLIST`（默认含可执行/脚本类型：`application/x-msdownload`、
   `application/x-executable`、`application/x-sh`、`text/x-shellscript`、
   `application/x-httpd-php` 等）命中 → 415 `unsupported_media_type`；
   `ASSET_ALLOWED_MIME_TYPES` 非空时，未在清单内 → 415。
4. **魔数嗅探**：无论声明什么，内容以 `\x7fELF` / `MZ` / Mach-O magic / `#!` 开头 →
   415。这一条才是「扫描」的实际内容——它拦的是**声明与内容不符**，而不是维护一份
   完整类型的白名单（后者永远追不上 provider 会产出的新格式）。

判定的纯函数放在 `apps/api/app/upload_guard.py`，`db_store.upload_asset` 在解码前后调用，
失败抛 `ApiError`（沿用 V7.1 的失败信封）。

### 2.4 资产签名 URL 策略：签名是叠加，不是替代

现状：`/assets/{id}/access-link` 已经能签发 HMAC 链接（`asset_link_secret`），
`/assets/{id}/content` 同时要求 `asset:read` **和**有效签名——也就是说**泄露一条链接
不等于泄露资产**，攻击者还缺一个租户身份。这个设计是对的，V8.4 只补两个缺口：

1. **TTL 上限**：`access-link` 现在接受调用方给的任意 `expires_in_seconds`——
   可以签一条十年后过期的链接。加 `ASSET_LINK_MAX_TTL_SECONDS`（默认 3600）**夹取**
   （超上限夹到上限，与 V7.4 embed token 的处理一致，而不是报错），`<= 0` 回落到默认值。
2. **默认密钥守卫**：`asset_link_secret` 默认值是 `"dev-only-change-me"`。生产环境
   （`app_env not in {local, dev, test}`）仍用默认值时，**拒绝签发**：
   503 `insecure_secret_configuration`。理由——默认密钥是公开的，用它签出的链接
   任何人都能伪造；让一个部署在「生产环境用开发密钥」这件事上静默成功，比让它 503 更糟，
   因为前者不会有人发现。校验只拦**签发**，不拦**验证**：已经发出去的链接在
   完成迁移前仍然可用。

### 2.5 与既有模块的关系

- **不复用 `embed.py` 的签名**：embed 令牌是「无状态身份」，payload 是可见的声明；
  provider 回调签名是「消息真实性」，payload 是任意请求体。二者共享的是**HMAC over
  `"{t}.{body}"` 这一个格式**，因此回调校验直接复用 `webhooks.py` 的
  `sign_webhook` / `verify_webhook` 助手（V7.3 已经把它做成纯函数），不新写签名代码。
- **`SecretBox` 不依赖数据库**：它只吃字符串，db 层的引用解析在 `repositories` / `db_store`。
  这样加解密可以在一行 SQL 都不开的情况下单测穷尽（包括 AAD 绑定、篡改检测、版本错配）。

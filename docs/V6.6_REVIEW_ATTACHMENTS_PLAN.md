# V6.6 Review Attachments（审核附件）计划

> 任务板 T85。V6 的最后一块拼图：**审核请求 ↔ 资产挂载**。审核人在关口不只看产物快照，
> 还能把证据素材（参考图、竞品视频、客户原始素材）直接挂在审核请求上，让决策有据可查。
> 本文档先写设计，实现完成后 §7 补真实钉值、§8 补测试与门禁清单。

## 1. 目标与非目标

**目标**

1. 审核请求可挂载资产：`POST /api/review-requests/{id}/attachments`。
2. 附件随 `ReviewRequestDetail` 一起返回（工作台一次请求拿全：决策 + 评论 + 待办 + 附件），
   附件内嵌资产快照（`asset: Asset`），工作台无需二次调用即可渲染缩略信息。
3. 挂载幂等：同一资产重复挂载返回既有行，不产生第二条（与资产库条目「重复加入不产生新条目」一致）。
4. 附件可移除：`DELETE /api/review-attachments/{attachment_id}`，硬删除（挂载是「指针」不是历史，
   移除行为落事件日志即可追溯）；移除后列表不再出现，再删 404。
5. 跨项目不泄露：资产必须属于审核请求所在项目，未知资产与跨项目资产一律 404（延续
   「未知实体 404、不 403」的既有哲学——403 会泄露「这个资产存在于别的项目」）。

**非目标**

- 不新增权限键（复用 `run:read` / `run:review`，权限键总数保持 18）。
- 不新增错误码（复用 404 `not_found` 信封与 `ReviewGateError` 形状）。
- 不做软删除（与资产库条目不同：条目有授权与复用语义需要保留墓碑，附件只是证据指针）。
- 不改审核决策/评论的行为——附件是旁路证据，不参与 artifact scope 校验、不锁定决策对象。

## 2. 数据模型

新表 `review_attachments`（migration `20261010_0017`，全库 31 → 32 张表）：

| 列 | 类型 | 说明 |
| --- | --- | --- |
| `id` | String(64) PK | `rvatt_` 前缀 |
| `tenant_id` | String(64) index | 租户 |
| `review_request_id` | FK review_requests.id, index | 挂在哪个审核请求上 |
| `run_id` | String(64) index | 冗余列：审计与事件检索不必 join |
| `asset_id` | FK assets.id, index | 挂载的资产 |
| `note` | Text nullable | 为什么要挂这张（「客户原始口播稿」「竞品参考」） |
| `added_by_user_id` | FK users.id nullable | 谁挂的 |
| `added_by_display_name` | String(160) nullable | 展示名 |
| `created_at` / `updated_at` | TimestampMixin | |

唯一约束 `(review_request_id, asset_id)`——幂等由数据库兜底，不只靠应用层先查。

**为什么挂载行引用 `asset_id` 而不复制资产**：审核附件的语义是「这张素材是这个决策的证据」，
证据必须指向原始素材（同 `storage_url`），复制反而制造两份需要保持同步的真相。这与
「复用资产到 run 时复制 + 记来源」不冲突——那是生成新资产（新的 `assets` 行），这里是引用。

## 3. API 契约

```
POST   /api/review-requests/{review_request_id}/attachments   run:review (SCOPE_COMMENT)
GET    /api/review-requests/{review_request_id}/attachments   run:read   (SCOPE_REVIEW)
DELETE /api/review-attachments/{attachment_id}                run:review (SCOPE_COMMENT)
```

- 请求体（POST）：`{"asset_id": "...", "note": "...", "added_by_user_id": "...", "added_by_display_name": "..."}`
  （后两者可选，与 `CreateReviewComment` 的作者字段对称）。
- 响应：`ReviewAttachment`（含内嵌 `asset: Asset` 快照）。
- `ReviewRequestDetail` 增加 `attachments: list[ReviewAttachment]`（默认空，向后兼容）。
- 失败形状不变：404 走 `HTTPException(404, ...)`（全局处理器补 `not_found`）。

## 4. 事件与审计

与评论一致（评论只写事件日志、不写 `audit_logs`）：

- `review.attachment_added`（payload：`asset_id` / `note` / `added_by_user_id`）
- `review.attachment_removed`（payload：`asset_id`）

## 5. 权限与钉值影响

- 无新权限键：挂载是审核动作（`run:review`），浏览是审核读取（`run:read`）。
- OpenAPI：**110 path / 139 operation**（+1 path +2 ops 的 attachments、+1 path +1 op 的删除）。
- `POLICY` 受控 115 → **118**；`OPEN_ENDPOINTS` 保持 21；错误码保持 22。
- `test_team_permissions.py` 与 `test_openapi_contract.py` 的钉值同步。

## 6. 门禁

新增第 19 节「审核附件」（17 项检查，总数 285 → 302）：
挂载到 `waiting_review` 关口的请求 → 重复挂载幂等（列表仍 1 条）→ Detail 内嵌附件与资产快照 →
跨项目资产 404 → 未知资产 404 → 未知请求 404 → 移除后列表消失 → 再删 404 →
`waiting_review` 之外的请求（approved）也可挂载（证据可以事后补）。

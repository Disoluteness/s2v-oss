# 能力补齐计划（Capacity Gap Plan）

更新时间：2026-11-09
基线：`1.0.1`（服务端 API 版本 `1.1.0`）

## 0. 这份计划解决什么问题

`docs/FULL_VERSION_ROADMAP.md` 记录的是 V0–V8 九个里程碑的收官状态，它回答的是
「规划内有没有漏项」。这份文档回答另一个问题：**把本项目的能力面与同类产品的
公开能力清单逐条并排看，还缺什么**，以及按什么顺序补、每批怎么验收。

对照基准是 OpenMontage 的**公开能力描述**（README 里的流水线、工具类目、治理机制）。

### Clean-room 纪律（本计划所有阶段都适用）

本项目只参考**能力层**：有哪几类流水线、哪几类工具、哪些治理动作值得做。

**不看、不搬**对方的源码、pipeline 定义文件、schema、prompt、skill 文本、UI 代码、
渲染器实现、目录组织。每一批落地时，设计要在本仓库里能独立讲清「为什么这样做」，
而不是「对方就是这么写的」。

具体执行方式：

- 只读对方的 `README` / 对外文档，不读 `lib/`、`schemas/`、`skills/`、`pipeline_defs/`。
- 新增文件从本仓库既有的 DSL、artifact 契约、工具合同出发，不从对方的结构出发。
- 每篇新策略文档都带一节 Clean-Room Boundary，写清「用了什么思路、实现从哪来」。

## 2. 差距清单与批次划分

批次按「依赖少、能独立验收、对产品完整度提升明显」排序。每批做完即可发布，
不攒到最后。

### P1 · 素材剪辑三条产线（最高性价比）

**补什么**：三条以「已有素材」为输入的生产线，复用 `source_clip_factory` 的
ingest → analysis → clip_selection → edit → export 骨架，但目标与审核标准不同。

| 新流水线 | 输入 | 与 `source_clip_factory` 的差别 |
| --- | --- | --- |
| `talking_head` | 真人出镜素材 | 候选评分看「观点完整度 / 钩子 / 口误密度」；字幕强制；静音段裁剪；构图以人像为中心 |
| `podcast_repurpose` | 长音频 | 转写**必需**（没有转写就选不出片段）；视觉层由封面/波形背景承担；每段必须有语义边界 |
| `cinematic` | 素材 + 音乐 | 候选评分看情绪曲线与镜头节奏，不看信息完整度；BGM 为主线；调色与转场进入审核项 |

**交付物**：3 个 pipeline JSON、3 篇策略文档、loader/发布测试、README 与版本说明同步。

**验收**：`GET /api/pipelines` 返回 10 条；三条新线各能建 run 走到 `final_review`；
预检对三条新线不出现 `blocked`（允许 `degraded`，例如无 BGM 供应商时）。

**动什么**：不新增表、不新增迁移、不新增工具目录条目、不改任何 JSON 契约字段。
只改 `pipeline 目录恰好 N 条` 这类计数钉值。

### P2 · 决策审计日志

**补什么**：把「为什么选这个供应商 / 这个风格 / 这个背景音乐」记成结构化条目，
而不只是操作审计（谁在什么时候改了什么）。

**设计要点（落地时定稿）**：一条决策记录包含 `category`、`subject`、`decision`、`chosen`、
`candidates`（含分数与排序位）、`confidence` + `confidence_basis`、`rationale`、`actor`。
四个写入点：执行计划生成（`tool_selection`，系统）、审核裁决（`review_decision`，人）、
质量降级接受（`quality_downgrade`，人）、首次付费确认（`paid_provider_consent`，人）。

`confidence` 定为**分数差距**（`score_margin` / `uncontested`）而不是概率；人工裁决一律留空，
避免被读成「系统对这个判断有 92% 把握」。

**交付物**：新表 + 迁移、`GET /api/runs/{run_id}/decision-log`、四个写入点、契约测试、
页面展示（run-board 面板）。

**验收**：跑一条 run 后能读到 `tool_selection` 与 `review_decision` 两类记录；
迁移 upgrade → downgrade → upgrade 往返通过；表数钉值同步。

**动什么**：migration（head 前进一位）、新增读端点（需进 `POLICY` 与
`OPEN_ENDPOINTS` 的精确划分）、表数钉值。

### P3 · 渲染前承诺校验

**补什么**：在合成前判断「计划说的是不是能做到的」，把明显会产出「带动画的 PPT」
的计划挡在渲染前，代价只是让人类确认一次。

**6 个信号**（全部从既有分析结果推导，不引入新模型）：

1. 静态图镜头占比 vs 声称的动态程度。
2. 平均镜头时长（过长 + 声称运动为主 → 冲突）。
3. 镜头意图缺失比例（分镜没有运镜/转场说明）。
4. 文字承载比例（字幕 + 标题占画面时间）。
5. 重复构图比例（相邻镜头相似度过高）。
6. 镜头数 / 目标时长比（不足以支撑宣称的节奏）。

**交付物**：`pre_render_check` artifact、判定逻辑、run 闸门（critical 需显式确认
`accept_quality_risk`）、页面提示。

**验收**：构造一个「90% 静态图 + 声称运动为主」的计划，run 停在闸门而不是直接渲染；
确认后可以继续；不确认则停在 `waiting_review`。

**动什么**：新增 artifact 类型；`run_gate` 增加一条分支（注意不能破坏既有闸门顺序）。

### P4 · 选择器可解释化

**补什么**：现有选择器是「资格筛选 + 质量分排序」，能把候选筛对，但说不清「为什么
是它」。改成多维加权 + 明细分，输出可以被 P2 的决策日志直接引用。

**维度**：任务契合、输出质量、控制能力、可靠性、成本、延迟、连续性。

**验收**：既有选择结果不变（用现有测试锁住）；每条候选都带 7 维明细与总分；
关掉的维度可配置（零权重）。

**动什么**：`tool_kit/selector.py` 内部结构；执行计划输出新增字段（**增量**，稳定面
字段不动）。

### P5 · 增强类工具

**补什么**：调色、响度归一化、画中画。三者都能用本地 FFmpeg 实现，不依赖供应商。

**交付物**：`ffmpeg_color_grade`、`ffmpeg_loudness_normalize`、`ffmpeg_picture_in_picture`
三个工具条目 + 新能力类 `color_grading` / `audio_processing`。

**验收**：工具目录 26 → 29；预检对三条新线显示这三项 `available`；门禁工具数钉值同步。

**动什么**：工具目录、能力类枚举、钉值。**不动**数据库。

### P6 · 素材检索 + 纪录片式蒙太奇

**补什么**：不付费用视频生成模型，也能用真实素材剪出片子。

**分两步**：
1. 本地素材目录工具（离线、零 key、带标签与许可字段），先让 `documentary_montage`
   在没有任何外部账号时能跑通。
2. 可选接一个免费素材源（需要 key，缺失时该工具 `unavailable`，流水线降级而不是失败）。

**检索方式**：关键词 + 标签匹配。**明确不做** embedding / CLIP 索引——那需要引入
模型依赖，与本项目「薄依赖、可离线」的取向冲突。

**验收**：零 key 环境下 `documentary_montage` 能产出带素材出处的成片；有 key 时
检索结果替换本地样例。

### P7 · 网络研究阶段与参考视频驱动

**补什么**：
- `research_brief`：写脚本前收集事实、数据点、受众问题，落成结构化简报，供审核。
- `reference_video_brief`：把一段参考视频拆成「结构 / 节奏 / 视觉手法」的描述，
  作为制作计划的输入（复用既有素材分析，不新增模型）。

**约束**：检索是**可选能力**。没有搜索供应商密钥时，阶段产出「研究未启用」的显式
记录，而不是伪造事实。这一点必须写进 artifact 与页面提示。

**验收**：无密钥时 run 正常推进并标注 `research_status: disabled`；有密钥时简报
带来源链接与抓取时间。

### P8 · 动效与角色一致性（最后做）

**补什么**：`animation`（纯动效/动态排版）与 `character_animation`（同一角色跨镜头）。

**为什么最后**：这两条要新增运行时能力——动效模板系统、角色设定资产、图生视频模型。
`canvas_renderer_kit` 已能做 HTML/Canvas 渲染，可以作为动效模板的起点；角色一致性则
依赖外部图生视频模型与一套角色设定契约。先做完 P1–P7，再评估投入。

## 3. 明确不做

| 项 | 理由 |
| --- | --- |
| 发布渠道（自动上传到平台） | 需要各平台账号授权与合规审查，超出「视频生产服务」边界 |
| 本地 GPU / 自建模型推理 | 与「薄依赖、可容器化部署」的定位冲突 |
| Agent-first 编排（把编排交给外部 AI 助手） | 本项目的价值是**服务端确定性编排**：可重放、可审计、可多租户 |
| Embedding / 向量检索索引 | 需要额外模型与存储，先用标签匹配验证需求 |
| 多租户子域名路由、真实计费 | 属于商业化阶段，见 `FULL_VERSION_ROADMAP.md` §2.2 |

## 4. 每批的收口动作（固定）

1. 代码 + 迁移（如有）+ 测试同批提交。
2. 钉值同步：pipeline 数、工具数、表数、门禁项数、`GET /api/pipelines` 计数。
3. 文档同步：`CHANGELOG.md`、`docs/VERSIONS.md`、README 的能力清单、
   本文件对应条目标记完成。
4. 自检：`ruff` + `node --check`（改页面时）+ 契约测试 + 门禁脚本。

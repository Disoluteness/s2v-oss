## 1. 目标与范围

把「一个 run 有没有超预算」升级成「一个团队这个周期还能花多少」：

1. **团队级配额**——`team_quotas` 表，按团队定义周期性的成本 / run 数 / token 上限；
2. **provider 用量归因**——把已有的 `usage_ledger_entries` 按「用量 → run → project → team」
   归到团队头上，让配额有可计算的分母；
3. **成本上限与审批**——hard 配额在启动与每次付费调用前拦截；soft 配额只警告；
   管理员可对单个 run 做**一次性豁免**（审批），豁免本身入审计。

沿用 T76 已经铺好的两条轨道，不另起炉灶：`run.input_payload.cost_budget` 是
**单 run** 预算，`team_quotas.limit_cost` 是**团队周期**预算；两者是不同层级的闸门，
同时生效，先拦住的先报错。

**明确不做（记录取舍）**：

- **不做真实计费账本 / 发票 / 支付**。平台没有收款方，`usage_ledger_entries` 记的是
  provider 成本，配额管的是「这个团队还能烧多少」，不是「客户欠多少」。
  多租户商业计费在 `FULL_VERSION_ROADMAP` 的 V1.0 不要求清单里已明确排除。
- **不做配额自动续期 / 分段阶梯 / 价格表**。一个团队一个周期一个上限，够用；
  价格换算属于 provider 适配层，已经在 `estimate_cost` 里。
- **不做新页面**。配额读写走 API（与 V8.1 / V8.2 同口径）；`/team` 页面已存在，
  加区块会牵动 `PAGE_ROUTES` 与页面门禁，收益不抵风险。
- **不动 worker 的处置逻辑**。配额是**入口闸门**，不是失败分类；超配额的调用根本
  不会发出，因此不产生新的 job 失败路径（`RunGateError` 在 T86 已显式
  `allow_auto_retry=False`）。

## 2. 设计决策

### 2.1 用量怎么归到团队：`projects.team_id`

`usage_ledger_entries` 只有 `tenant_id` + `run_id`，没有团队维度；`production_runs`
有 `project_id`，`projects` 有 `tenant_id` —— 但 T79 引入 `teams` 之后，**项目并没有
真正归属任何团队**（团队只是个成员容器）。团队级配额要成立，这条边必须补上。

- `projects` 新增可空列 `team_id`（FK → `teams.id`，带索引）。
- **`team_id IS NULL` 视为默认团队**。理由：迁移发生时默认团队可能还不存在
  （它在首次有人入座时懒创建），backfill 会写出悬空外键或依赖一个未必存在的行；
  而「没指定团队的项目就是默认团队的」与 `ActorContext.is_default` 的既有语义一致
  （未入座的身份也只在默认团队里有座位）。
- 归因路径固定为 `usage_ledger_entries.run_id → production_runs.project_id →
  projects.team_id`。查询在目标团队是默认团队时把 `team_id IS NULL` 一并算入。

### 2.2 配额是列不是流水：一团队一行

`team_quotas`（唯一约束 `team_id`），每团队至多一行当前生效配额：

| 列 | 说明 |
|---|---|
| `id` | `quota_<hex12>` |
| `tenant_id` | 归属租户（索引） |
| `team_id` | FK → `teams.id`，**唯一** |
| `period` | `calendar_month` / `rolling_30d` / `lifetime` |
| `limit_cost` | Numeric(12,6)，`NULL` = 不限 |
| `limit_runs` | Integer，`NULL` = 不限 |
| `limit_tokens` | BigInteger，`NULL` = 不限 |
| `enforcement` | `hard`（阻断）/ `soft`（只警告） |
| `status` | `active` / `paused`（`paused` 等同不生效） |
| `created_by` / `note` | 审计用 |

**为什么不做配额历史表**：改配额要留痕，但痕应该在审计流水（`audit_logs`，
V6.5 已有）而不是配额表里；把每次调整写成一行会让「当前生效配额」变成一个
需要 `ORDER BY created_at DESC LIMIT 1` 的查询，而团队配额是被**每次付费调用**
读取的热路径。一行 + 审计事件是正确取舍。

### 2.3 周期窗口：三个枚举，窗口在读取时算

- `calendar_month`：当月 1 日 00:00 UTC → 下月 1 日 00:00 UTC；
- `rolling_30d`：`now - 30d` → `now`；
- `lifetime`：无下界 → `now`。

**不存窗口起止**。窗口是 `period` 的纯函数，存下来就必须有人负责翻页（否则每次
跨月都要有 job 去重置），而按需计算既没有这个状态，也不会在跨月时刻前后不一致。
`apps/api/app/quota.py` 的 `quota_window()` 是唯一实现，测试直接打它。

### 2.4 闸门：hard 阻断、soft 警告、豁免放行

`_assert_team_quota_allows(run_id, *, estimated_cost, operation)` 挂在两个既有闸门上：

- `_assert_cost_reservation_allows`（run **启动**，T76）——用 execution plan 的
  `reserved_cost` 作为追加额，一次拦住「整个 run 都装不下」的情况；
- `_assert_budget_allows`（每次**付费调用**前，6 个调用点）——用本次预估追加额。

判定（`quota.py::evaluate_quota`）：

- 配额不存在 / `status=paused` / 全部 `limit_*` 为 `NULL` → `not_configured`，放行
  （**不写事件**：没配额度的团队每次付费都写一条警告会把事件日志淹掉）；
- 任一项在追加后越界：
  - `enforcement=hard` → `RunGateError("team_quota_exceeded", status 400)`，
    details 带 `period` / 各项 `limit` / `projected` / `current` / `additional`；
  - `enforcement=soft` → 落 `run.team_quota_warning`（warning 级）后放行；
- 通过时**不另写事件**，而是把判定结果挂到 run 启动那条
  `run.cost_reservation_recorded`（T76 已有，每次 run 仅一条）的 `team_quota` 字段：
  配额存在时是一个含 `period_status` / `limits` / `current` / `projected` 的对象，
  不存在时为 `null`。「未受管的 run 不该是隐形的」这条由它承载 —— 若在**每次付费调用**
  上各写一条 checked 事件，一个 6 次付费调用的 run 会写 6 条同义 INFO，把事件日志淹掉，
  而 run 启动那条本来就足够回答「这个 run 起跑时团队还有多少额度」。

**豁免（审批）优先于 hard**：`run.input_payload.quota_override` 存在且 `accepted`
时，hard 也放行，并落 `run.team_quota_overridden`。豁免的实现完全复制 T76 的
`paid_provider_consents` 模式（写在 run 的 `input_payload` 里、以 run 为粒度、
可撤销），因为它同样回答「有人明确同意这一次越过防线」。

**谁能豁免**：`quota:manage`（租户级），**不是** `run:start`。T76 的付费确认用
`run:start` 是合理的（那是「这个 run 用这个 provider 吗」），但配额豁免是
「越过团队的钱包上限」——如果 `run:start` 就能豁免，团队 member 人手一个
`run:start`，hard 配额等于没有。所以豁免必须由配额管理者点头。

### 2.5 权限键与错误码

新增两个权限键（18 → **20**）：

- `quota:read`——看团队配额与用量。**不进** `TENANT_ONLY_PERMISSIONS`：
  它以 `:read` 结尾，自动进入 `READ_ONLY_PERMISSIONS`，语义与既有的
  「只读角色能看只读数据」一致；用量聚合本身是只读视图。
- `quota:manage`——改配额、批准豁免。**进** `TENANT_ONLY_PERMISSIONS`（第 5 个）：
  它决定整个租户的**花钱上限**，与 `team:manage` / `apikey:manage` /
  `webhook:manage` / `integration:manage` 同一条线——项目角色不能给。
  ADMIN 因 `ALL - {TEAM_MANAGE}` 自动持有；MEMBER / VIEWER 不持有。

新增一个错误码（22 → **23**）：`team_quota_exceeded`，类别 `gate`，HTTP 400，
**不可重试**（与 T76 的 `cost_budget_exceeded` 同族）。

### 2.6 端点（6 个，全部走既有 SCOPE，不引入新 scope）

| 方法 | 路径 | 权限 / 作用域 | 说明 |
|---|---|---|---|
| GET | `/api/team-quotas` | `quota:read` / tenant | 全租户配额总览（含窗口用量） |
| GET | `/api/teams/{team_id}/quota` | `quota:read` / tenant | 单团队配额 + 窗口用量 |
| PUT | `/api/teams/{team_id}/quota` | `quota:manage` / tenant | upsert（无则建，有则改） |
| DELETE | `/api/teams/{team_id}/quota` | `quota:manage` / tenant | 删除 → 回落「未配置」 |
| POST | `/api/runs/{run_id}/quota-override` | `quota:manage` / run | 批准/撤销一次豁免 |
| PATCH | `/api/projects/{project_id}/team` | `quota:manage` / project | 移动项目归属（`null` = 默认团队） |

**第 6 个端点（归属）在计划定稿后补入**：原先只打算让 `projects.team_id` 由带外方式设置，但这样配额在多团队下不可用；而若让 `POST /api/projects` 直接接受 `team_id`，任何 `project:write` 持有者都能新建一个项目指向无配额团队来逃逸上限。所以归属改为**只由 `quota:manage` 走专用端点移动**，`ProjectCreate` 不暴露该字段。

**团队配额端点沿用 `SCOPE_TENANT`**（与既有的 `/api/teams/{team_id}` 一族一致）：
团队是租户级资源，`_resolve_project_id` 对 `tenant` 返回 `None`，判定走团队角色——
这正是想要的（配额不属于任何一个项目）。豁免端点用 `SCOPE_RUN`，因为它落在某个
具体 run 上；`quota:manage` 是租户级键，项目角色给不了，所以 `SCOPE_RUN` 的
项目角色判定不会让它逃逸（`test_project_role_can_never_grant_a_tenant_only_permission`
的同类守护）。

# V7.2 SDK 实施计划

状态：DONE（2026-10-09）
前置：T80 / V7.1 HTTP API v1 契约（统一失败信封、可选幂等键、分页信封、spec 与权限表对齐）
对应任务：T81
新增 migration：`20261010_0014`（`api_keys`，全库 28 张表）

## 1. 目标

V7.1 把 API 变成了一份**稳定的契约**，但契约只能被「会写 HTTP 的人」消费：调用方要自己拼
body、自己识别 `{"detail": {code, ...}}`、自己在失败后决定能不能重试。V7.2 要解决的是
**最后一公里**——让内部 AI 平台不接触底层 provider、不读 spec，就能直接创建并等待一个视频 run。

验收标准（来自 `docs/FULL_VERSION_ROADMAP.md` §V7）：

- 内部 AI 平台可以不接触底层 provider，直接通过 SDK 创建并等待一个视频 run。
- SDK 示例覆盖脚本到成片、上传素材、参考视频、失败重试。

同时必须解决一个前置缺口：**API 没有编程访问凭证**。V6.5 的 `X-Actor-Id` 是「网关告诉我
谁在调」，只适用于浏览器同源场景；一个跑在别人服务器上的程序不能靠伪造请求头来获得身份。
因此 V7.2 = `api_keys` + 三个管理端点 + 两个 SDK。

## 2. 落地范围

### 2.1 凭证：`api_keys` 表与密钥格式

新增表 `api_keys`（migration `20261010_0014`）：`id` / `tenant_id` / `actor_id` / `name` /
`key_prefix` / `key_hash` / `scopes` / `status` / `created_by` / `last_used_at` / `expires_at`
+ 时间戳。列名用 `key_prefix` / `key_hash` 而不是 `prefix` / `hash`，因为 MySQL 8 里 `key` 是
保留字（与 `idempotency_key` 同一个理由）。

密钥格式：`s2v_<12 hex>_<48 hex>`。

- 用**十六进制**而不是 urlsafe base64：`_` 在 base64url 里是合法字符，会让「按 `_` 切成三
  段」这个解析动作产生歧义。
- `key_prefix`（`s2v_<12hex>`）是**非秘密**的检索句柄，带唯一索引；`key_hash` 是
  `SHA-256(API_KEY_PEPPER + 明文)`。**明文只在签发响应里出现一次**，之后无法再取出。
- 比对用 `hmac.compare_digest`，不是 `==`。
- `actor_id` **故意不设外键**——它是外部身份系统里的 id，与 `audit_logs.actor_id` 同一个
  道理；签发时通过 `UserRepository.ensure_user` 登记（与 T77 的教训一致，`users` 行不能假设存在）。

`scopes = None` 表示「所有者的全部权限」，非 `None` 表示**收窄**。签发时校验：
未知权限键 → 400 `bad_request`；超出所有者当前有效权限 → 403 `permission_denied`
（`scopes ⊆ owner 的有效权限`，只减不增）。

新增权限键 `apikey:manage`（第 16 个），与 `team:manage` 同属**租户级权限**
（`TENANT_ONLY_PERMISSIONS`）——项目角色永远不会授予它，因为「签发一个能代表你写库的凭证」
不是项目内的协作动作。团队 `admin` 及以上可签发。

### 2.2 鉴权并入统一身份入口

**关键决策：凭证是「身份」，不是「权限」。** 一个 API key 解析出的就是一个 `ActorContext`，
和 `X-Actor-Id` 走**同一条**判定路径。这样 scope 收窄只有一个落点，不会出现「某个端点忘了
检查 token」的漏洞。

`apps/api/app/api_keys.py` 提供应用级依赖 `enforce_api_key_identity`，挂载顺序在权限守卫与
幂等守卫**之前**（要先知道「我是谁」才能判定权限）：

```
enforce_api_key_identity  →  enforce_api_permissions  →  enforce_idempotency
```

三个不可回退的取舍：

1. **`Authorization: Bearer` 优先于 `X-Actor-Id`。** 显式凭证比网关隐式身份更可信。
2. **没有 `Authorization` 头的请求完全不受影响。** 与 `Idempotency-Key` 同样的「可选能力」
   策略——这是既有 5 个页面、MVP 样片链路与部署门禁零改动的前提。
3. **非 Bearer 的 `Authorization`（如 Basic）不算鉴权尝试**，请求照常回退到请求头/默认身份，
   而不是失败。

鉴权失败只可能是**一种**结果：未知、已吊销、已过期、格式畸形、密钥不符，全部返回
401 `api_key_invalid`，不泄露是哪一种。成功鉴权会 `touch` `last_used_at`。

### 2.3 scope 收窄的执行点

唯一的判定点在 `DatabaseStore.require_permission(actor, permission, *, key_scopes=...)`：

```python
seat_allows   = permission in effective_permissions(team_role, project_role)
out_of_scope  = seat_allows and key_scopes is not None and permission.value not in key_scopes
if seat_allows and not out_of_scope:
    return
reason = "api_key_scope" if out_of_scope else "seat"
```

「越界」与「席位不足」都是 403 `permission_denied`，但在审计里可区分：
`permission.denied` 的 payload 带 `reason` 与 `api_key_prefix`，响应体 message 写明
`api key is not scoped for 'project:write'`。**拒绝必须先落审计并 commit 再抛出**，
否则证据会随请求中止回滚（沿用 V6.5 的既有做法）。

### 2.4 管理端点

```
POST /api/api-keys                     签发（响应含一次性明文，response_model=ApiKeyCreated）
GET  /api/api-keys                     Page 信封，绝不含明文
POST /api/api-keys/{api_key_id}/revoke 吊销
```

三者都是 `apikey:manage` + 租户作用域。吊销是**幂等**的：重复吊销返回同一个 `revoked` 状态
而不是报错，且**只写一条审计**（见 §3 的缺陷记录）。吊销未知 id → 404。

`/api/me` 在带 key 调用时报告**收窄后**的权限集，因此客户端可以自查「我这个 key 能做什么」。

### 2.5 Python SDK

`sdk/python/`，导入名 `s2v`，发行版名 `s2v-client`，**零运行时依赖**。

核心是可插拔的传输层：一个 `Transport` 协议执行一次 HTTP 交换并返回
`Response(status, headers, body_bytes)`，**不对 4xx/5xx 抛异常**（错误解码属于上层）。
默认实现是 `UrllibTransport`。这让调用方可以在自己的框架里接管网络（重试、代理、埋点），
也让测试可以注入 `tests/harness.py` 里的 `AsgiTransport`——**SDK 测试直接打到进程内 ASGI
应用，不需要 httpx，也不需要起服务**。

业务封装（路线图点名的六个 + 支撑它们的完整覆盖面）：

| 路线图要求 | SDK 方法 |
| --- | --- |
| `createRun` | `create_run()` |
| `uploadAsset` | `upload_asset()` / `upload_person_image()` |
| `startRun` | `start_run()`（含 `accept_intent_downgrade` / `accept_paid_providers`） |
| `waitRun` | `wait_run()` |
| `getFinalVideo` | `get_final_video()` |
| `retryAction` | `retry_action()` / `retry_job()` / `retry_failed_jobs()` |

再加：`create_project` / `get_run_board` / `list_run_artifacts` / `list_run_jobs` /
`list_run_events` / `submit_review_decision` / `download_asset` / `confirm_paid_provider` /
`run_state_action` / `create_api_key` / `list_api_keys` / `revoke_api_key`，以及两个一站式
入口 `run_script()` 与 `script_to_video()`。

`wait_run()` 的语义是**有意义的停点**，不是「等到跑完为止」：

- 到达终态（`TERMINAL_RUN_STATUSES`）→ 返回 run。
- 停在 `BLOCKING_RUN_STATUSES`——即**需要人工介入**（审核关口）——默认返回而不是死等，
  只有 `stop_on_review=False` 才继续等。
- 超时可选择抛 `RunWaitTimeout` 或返回当前 run。
- `on_progress(run)` 回调让调用方可以打日志。

模型层是轻量的 `Model` 封装（`Project` / `Run` / `Asset` / `Artifact` / `Job` /
`FinalVideo` / `Actor` / `ApiKey` / `Page`）：既能用属性访问，也保留 `.raw` 与
`__getitem__`，**服务端加字段不会打挂客户端**。`get_final_video()` 从 run board 的
`final_outputs` 里挑：优先 `rendered_video`，其次 `edited_video`，再退到任意 `video/*`。

### 2.6 TypeScript / Node SDK

`sdk/typescript/`，npm 名 `s2v-client`，ESM + `NodeNext`，`strict` + `noUncheckedIndexedAccess`，
编译产物在 `dist/`。与 Python 版一一对应，命名用驼峰（`createRun` / `uploadAsset` …）。

**与 Python 版唯一的实质差异：传输层的响应体是 `Uint8Array`，不是 `string`。** 同一个客户端
要下载 MP4，任何 UTF-8 解码/重编码都会破坏二进制。JSON/文本响应走导出的 `bodyText()`
辅助函数。默认传输是全局 `fetch`，用 `AbortController` 做超时并在 `finally` 里清理定时器。
`toBase64` 优先用 `Buffer`。

### 2.7 幂等键与重试

SDK 在**所有变更调用**上默认自动生成 `Idempotency-Key`（`auto_idempotency=True`），
读取类调用不带。**重试复用同一个 key**，所以「网络抖动导致的重试」不会产生第二个 run。

重试条件是 `429` / `5xx` / `RETRYABLE_CODES`（`rate_limited`、`internal_error`、
`bad_gateway`、`service_unavailable`、`idempotency_in_progress`），并**遵循 `Retry-After`**。
400/403/404/409/422 一律不重试——它们重试一万次也是同一个结果。

副作用：由于默认加幂等键，`idempotency_keys` 表的行数会随请求量增长。因此
`BackgroundJobWorker` 新增带速率限制的 `_housekeeping()`，按
`WORKER_PURGE_INTERVAL_SECONDS`（默认 300s）调用 `purge_expired_idempotency_keys()`。

- `tests/test_sdk.py`（36 项）：通过 `AsgiTransport` 打真实应用，覆盖鉴权、六个业务封装、

- `tests/harness.py`：从 `test_api_contract.py` 提取出的共享 ASGI 测试件
  （`AsgiClient` / `build_client` / `AsgiTransport`），两个测试文件驱动同一套栈。
- 固定数量同步：`Permission` 15 → **16**、`POLICY` ∪ `OPEN_ENDPOINTS` 注册路由
  115 → **120**、受控 97 → **101**、开放 18 → **19**、OpenAPI 96/117 → **98 path / 120 operation**。
- 部署门禁新增**第 16 节**（25 项）：签发与一次性明文、Bearer 身份、真实写入、三类不可用
  key 一致返回 401、非 Bearer 不影响身份、scope 收窄与越界理由、未知 scope 400、吊销与
  幂等重放、SDK 六个业务端点全部在 spec 中、每个 `/api` operation 都声明 401。
- 结果：全量测试 **384 passed, 1 skipped**；ruff 通过；`tsc -p sdk/typescript/tsconfig.json`
  退出码 0 且 5 个 `dist/*.js` 通过 `node --check`；migration 往返 28 → 27 → 28 张表
  （`alembic_version = 20261010_0014`）；门禁 **207 项检查全通过**。

**修掉一个真实缺陷**：吊销原先无条件写 `apikey.revoked` 审计，导致重复吊销产生两条审计
记录（`test_revoking_is_immediate_and_idempotent` 断言 `2 == 1` 失败）。修复方式是让
`ApiKeyRepository.revoke` 返回 `ApiKeyRevocation(api_key, changed)`，Store 只在
`changed` 为真时落审计并 commit。

## 4. 明确不做的事

- **不做真实登录 / IdP。** `api_keys` 回答「这个程序化调用被授权做什么」，身份本体仍来自
  外部系统；`actor_id` 只是一个字符串。
- **不做多租户路由。** 表里有 `tenant_id`，但所有查询仍落在单一默认租户上；租户隔离是 V8
  之后的事。
- **不做 scope 的层级/通配。** scope 是权限键的精确集合，没有 `project:*` 这类通配符。
- **不做 SDK 自动生成。** 两个 SDK 是手写的薄封装，不是 spec 生成器产物——生成器留给后续
  版本；手写换来的是 `wait_run` / `get_final_video` 这类「业务语义」封装，它们本身不在
  spec 里。
- **不做 Webhook。** 长任务的推送通知属 V7.3，V7.2 只提供轮询式 `wait_run()`。
- **不做重试的持久化。** SDK 的重试是进程内的；跨进程的可靠性依赖幂等键，而不是重试队列。

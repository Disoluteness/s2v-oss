# V7.3 Outbound Webhook — 设计与落地记录

状态：**已完成（T82）**。前置：V7.1 错误信封 / 幂等键（§V7.1）、V7.2 API key 身份（§V7.2）。

## 1. 目标与验收

平台已把每次状态变化写进 `event_logs`，但只会"拉"（轮询 / board）的调用方无法及时知道
「阶段进入人工审核」「成片合成完成」。V7.3 提供**出站 webhook**：租户注册自己的 HTTPS
端点，平台把匹配的已发布事件以**带签名的 POST** 推过去。

验收标准：

1. 订阅方可以**先看目录再订阅**——`GET /api/webhook-events` 公开、静态、无租户数据。
2. 事件成功写入 `event_logs` 的**同一个事务**里就产生了投递行（事务性 outbox），
   「事件发生了但没人被通知」不是数据库可达的状态。
3. 投递**至少一次**（at-least-once）且带重试与退避；尝试耗尽变成 `abandoned` 而**不是
   静默丢弃**；连续失败的端点被自动停用。
4. 每次投递携带可独立校验的签名，接收方用一个函数就能完成防篡改 + 防重放校验。

## 2. 事件词汇表（公开契约）

六个发布事件（`apps/api/app/webhooks.py` 的 `WebhookEvent`），与内部事件类型的映射：

| 发布事件 | 内部来源（`event_logs.event_type`） | 说明 |
| --- | --- | --- |
| `run.started` | `run.started` | run 通过预检并开始执行 |
| `run.completed` | `run.completed` | run 走到终态并完成 |
| `stage.waiting_review` | `stage.waiting_review` | 阶段进入人工审核等待 |
| `job.failed` | `job.failed` | 后台任务失败 |
| `render.completed` | `job.final_composed` | 成片合成完成，可下载 |
| `publish.completed` | `job.publish_package_created` | 发布包已生成 |

两个刻意的设计点：

- **间接映射是全部重点**：改名内部事件（或换掉合成视频的 job）不应悄悄掐断客户的
  端点。`WEBHOOK_EVENT_SOURCES` 是吸收内部变更的唯一位置。
- **`run.completed` 与 `render.completed` 刻意分开**：run 可以在不产视频的流水线上
  完成（文档交付物），渲染也可以由随后等待人工的 run 完成。合并会让其中一个不可用。
- 事件类型过滤在 Python 侧做而不是 SQL：`event_types` 是 JSON 数组，SQLite/MySQL 都
  没有可移植且可索引的包含谓词；单租户订阅是个位数的行，扫描不是这里的成本。

## 3. 事务性 outbox

`EventRepository.append_event`（所有事件的唯一收口点）在**同一事务**里调用
`WebhookRepository.enqueue_for_event`：把内部事件映射成公开名，找出该租户匹配的活跃
订阅，逐个写 `webhook_deliveries` 行。行内 `payload` 是**事件快照**（复制而非引用），
含 `delivery_id / event_id / event_type / run_id / project_id / sequence /
occurred_at / severity / message / stage_key / data`——重投时投递仍然自描述。

之后的一切是 at-least-once：worker 认领（`claim_pending_deliveries`，带租约与
`FOR UPDATE SKIP LOCKED`）→ 带签名 POST → 记账（`settle_webhook_delivery`）。

## 4. 签名与验证

头 `X-S2V-Signature: t=<unix>,v1=<hex>`，HMAC-SHA256 over `"{t}." + body`，
密钥是订阅的 `secret`（32 字节熵 hex，`String(64)`）。

- **时间戳在签名串里**：接收方拒绝超过容差（默认 300s，Stripe 时代默认值）的签名即
  获得防重放；攻击者无法既改时间戳又保持摘要有效。
- **一个头而不是两个**：时间戳不能脱离它绑定的摘要被单独替换。
- 投递还带 `X-S2V-Delivery-Id`（接收方去重的稳定键）、`X-S2V-Event-Id`、
  `X-S2V-Event-Type`、`X-S2V-Attempt`（1 起）。
- SDK 双方都内置校验：Python `s2v.verify_webhook_signature`、TS
  `verifyWebhookSignature`（`node:crypto`，`timingSafeEqual`），测试向量跨语言一致。
- **secret 明文存储且每次读取都回显**——与 API key 相反。区别在谁持密钥：API key
  认证「调用方→平台」，泄露即失陷；签名密钥只让持有者校验平台**已经发给它**的消息，
  藏着它只会逼订阅者每次部署都轮换。落盘加密与 provider 密钥一样归 V8.4 统一处理。

## 5. 重试策略

- 只有 **2xx**（`[200, 300)`）算成功；**3xx 不跟随**——端点的归宿由订阅者的配置决定，
  追重定向会让投递悄悄搬到订阅者从未注册的地方。
- 退避 `retry_delay_seconds(attempt) = min(cap, base * 2^(attempt-1))`，默认
  base 30s / cap 1h；投递行自带 `max_attempts`（默认 6）。
- 尝试耗尽 → `abandoned`（`next_attempt_at IS NULL`），可被手动重投救回；
  `requeue` 重置 attempt 计数——手动重投的含义是「端点修好了」，带着旧计数只会更快放弃。
- **自动停用**：`note_subscription_failure` 累计连续失败，达到阈值（默认 20）把订阅
  置为 `disabled`（与人工 `paused` 区分：行自己说明为什么停了）。成功清零计数；
  人工重新激活也清零，否则修好后的第一次失败会立即再触发停用。耗尽型（abandoned）失败
  **不**计入连续失败——只有「还在重试」的失败才说明端点当前持续坏着。
- `delivering` 状态带租约（默认 300s），租约过期可被其他 worker 认领——worker 崩溃时
  在途投递会回来，而不是停在没人会离开的状态。
- `webhook_dispatch_enabled=false` 可整体关闭 worker 的 webhook 循环。

## 6. 权限与端点

第 17 个权限键 `webhook:manage`，加入 `TENANT_ONLY_PERMISSIONS`——订阅的端点会收到
**全租户每个 run** 的事件，把它塞进单个项目的角色是对授予范围的撒谎。

| 方法与路径 | 权限 | 说明 |
| --- | --- | --- |
| `GET /api/webhook-events` | 开放 | 静态目录，不含租户数据 |
| `GET / POST /api/webhooks` | `webhook:manage` | 列表 / 注册 |
| `GET / PATCH / DELETE /api/webhooks/{id}` | `webhook:manage` | 详情 / 部分更新 / 删除 |
| `POST /api/webhooks/{id}/rotate-secret` | `webhook:manage` | 轮换签名密钥 |
| `GET /api/webhooks/{id}/deliveries` | `webhook:manage` | 投递台账 |
| `POST /api/webhook-deliveries/{id}/requeue` | `webhook:manage` | 手动重投 |

策略表 `POLICY` +8 条受控、`OPEN_ENDPOINTS` +1 条开放（现 **129 注册 / 109 受控 /
20 开放**）；OpenAPI **104 path / 129 operation**，与两表精确相等（契约测试钉住）。
管理动作审计：`webhook.subscription_created / subscription_updated /
subscription_deleted / secret_rotated / delivery_requeued`。
跨租户 id 一律读作不存在（404），不泄露存在性。

## 7. worker 接入

`BackgroundJobWorker.run_once` 在处理完后台任务后调用
`_dispatch_webhooks(store, session)`：`WebhookDispatcher.dispatch(store, worker_id,
limit=webhook_batch_size)`，全程 try/except 包裹——死端点绝不能拖垮任务处理。
dispatcher 与传输解耦（`WebhookTransport` 协议 + 默认 `UrllibWebhookTransport`，
仅标准库），重试/退避/停用逻辑因此可以在没有 socket 的单测里穷尽。
worker 新增配置见 `.env.example` 的 `WEBHOOK_*`。**T82 同时改了 api 与 worker，
部署时两个镜像都要重建。**

## 8. 数据模型（migration `20261010_0015_webhooks`）

全库 **30 张表**（15 个 migration）。

- `webhook_subscriptions`：`id(whsub_) / tenant_id / name / url / secret /
  event_types(JSON) / status(active|paused|disabled) / description / created_by /
  last_success_at / last_failure_at / consecutive_failures`。
- `webhook_deliveries`：`id(whdel_) / tenant_id / subscription_id(FK, 级联删除) /
  event_id / event_type / run_id / status(pending|delivering|succeeded|failed|abandoned)
  / attempt / max_attempts / payload(JSON) / signature / response_status /
  response_body(截断至 2000 字符) / error_message / next_attempt_at / delivered_at /
  locked_by`。`event_id / run_id` 是普通索引列而非外键——投递是快照，绑到可变的行上
  会让记录不再表达它入队时所说的话。
- 删除订阅级联删除其投递：永远不会被排空的队列不值得保留，事件日志仍保有源事件。
- migration 做了 upgrade → downgrade → upgrade 往返验证（30 → 28 → 30）。

## 11. 已知的取舍与边界

- 门禁不等待真实投递（本地门禁无 worker）；投递语义由单测 + 部署环境人工核对。
- secret 与 provider 凭证一样明文落盘，加密归 V8.4。
- 事件载荷是 `event_logs.payload` 的快照，不保证跨版本稳定字段集；稳定的是信封字段
  （§3 列表）与 `event_type` 词汇表。
- 订阅去重是接收方的责任（`X-S2V-Delivery-Id`）；平台只承诺 at-least-once。
